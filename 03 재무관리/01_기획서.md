# MyFin V2.0 통합 아키텍처 설계서

> **시스템 분류:** 개인용 멀티 계좌 자동 트레이딩 플랫폼
> **인프라 제약:** 8GB RAM 가상 머신(VM) 단일 노드
> **아키텍처 패턴:** CQRS · Layered Architecture · Event-Driven (Pub/Sub)

---

## 1. 프로젝트 정의 및 범위

### 1.1 시스템 목적

MyFin V2.0은 다중 증권사·거래소 API 키를 암호화 보관하고, 사용자 정의 조건 기반 자동 트레이딩 봇을 운용하며, 거래 로그를 Elasticsearch에 적재하여 LLM 기반 사후 분석 보고서를 자동 생성하는 **개인용 올인원 자산 트레이딩 플랫폼**이다.

### 1.2 설계 제약 조건 (Hard Constraints)

| 항목 | 값 | 결정 근거 |
| --- | --- | --- |
| 물리 RAM | 8 GB | VM 스펙 고정 |
| 운영체제 | Ubuntu 22.04 LTS | LTS 지원 주기 (2027년 EOL) |
| 배포 방식 | Docker Compose v2 | Kubernetes 최소 요구 RAM 초과 (etcd 300MB+) |
| 예상 동시 사용자 | 1인 (개인) | 향후 소규모 팀 확장 설계 허용 |
| **프론트엔드** | **React 19 + Vite 6** | 아래 근거 참조 |
| 백엔드 언어 | Python 3.12 | |
| API 프레임워크 | FastAPI 0.111+ | 비동기 처리, 자동 OpenAPI 스펙 생성 |
| ORM | SQLAlchemy 2.0 (async) | 타입 안전성, 비동기 드라이버 지원 |

> [!note] React 19 + Vite 6 선택 근거
> 개발 서버(dev mode)는 VM이 아닌 **개발 머신 로컬**에서 구동하고, VM에는 `vite build` 빌드 산출물(정적 파일)만 Nginx로 서빙한다. 따라서 8GB VM에서 Node.js 메모리 경합은 발생하지 않는다. React 19의 Concurrent 렌더링과 성숙한 생태계(TanStack Query, Zustand, React Router v7)가 트레이딩 대시보드의 실시간 데이터 업데이트 요구사항에 최적합하다.

### 1.3 설계 비기능 요구사항 (Non-Functional Requirements)

| ID | 항목 | 목표값 | 측정 방법 |
| --- | --- | --- | --- |
| NFR-01 | API 응답 시간 (p95) | ≤ 200ms (RDB 조회) | FastAPI 미들웨어 로깅 |
| NFR-02 | API 응답 시간 (p95) | ≤ 500ms (ES 집계) | ES 슬로우 쿼리 로그 |
| NFR-03 | 주문 실행 지연 | ≤ 1,000ms (봇 → 증권사) | `execution_latency_ms` 필드 |
| NFR-04 | 시스템 가용성 | ≥ 99% (월 기준 ~7시간 다운 허용) | Uptime 모니터링 |
| NFR-05 | Kill-Switch 반응 시간 | ≤ 2초 (UI 클릭 → 봇 중단) | Redis Pub/Sub RTT |
| NFR-06 | 메모리 한도 | OOM Killer 발동 0회/월 | cgroup 통계 |

## 2. 아키텍처 원칙 (Architecture Principles)

| ID | 원칙 | 내용 |
| --- | --- | --- |
| P-01 | Zero Trust API Management | API Key 평문 저장 절대 금지. Application Layer AES-256(Fernet) 암호화 후 저장. Master Key는 OS 환경변수로만 주입. 코드·DB와 완전 분리 |
| P-02 | Loose Coupling | 특정 증권사 API 장애가 타 계좌 봇에 전파되지 않도록 계좌별 Celery Worker 프로세스 격리 + Circuit Breaker 패턴 적용 |
| P-03 | CQRS 책임 분리 | 쓰기(Command): PostgreSQL (ACID 보장), 대용량 분석 읽기(Query): Elasticsearch (역색인 집계). 단일 DB 과부하 방지 |
| P-04 | Resource-Constrained Optimization | 컴포넌트별 `mem_limit` + `memswap_limit` Hard Limit. Elasticsearch SWAP 완전 차단 (`memory_lock`) |
| P-05 | Security by Design | OWASP Top 10 방어를 코드·인프라 레이어 모두에 적용. 보안은 기능 개발 이후 추가가 아닌 설계 단계 내재화 |
| P-06 | Operability First | 모든 서비스는 `/health` 엔드포인트 보유. 구조화 JSON 로그를 ES로 수집. 알람 임계치를 사전 정의 |

### 3.2 실시간 이벤트 흐름 (Kill-Switch 시나리오)

```text
[사용자] PATCH /accounts/1/kill-switch { is_active: false }
    │
    ├─ 1. FastAPI: JWT 검증 + 소유권 확인 (user_id 일치 여부)
    │
    ├─ 2. PostgreSQL: UPDATE user_accounts SET is_active = false WHERE id = 1
    │
    ├─ 3. Redis PUBLISH: channel "user:42:events"
    │          payload: { event: "KILL_SWITCH", account_id: 1, is_active: false }
    │
    ├─ 4a. Celery TradingBotWorker (Subscriber)
    │          → 진행 중인 주문 요청 즉시 중단
    │          → 신규 룰 평가 루프 정지
    │
    └─ 4b. FastAPI WebSocket Handler (Subscriber)
               → WS PUSH → React 클라이언트 (UI 즉시 업데이트)
```

| 시장 | 데이터 소스 | 프로토콜 | 수집 주체 | 저장소 | API 참조 |
| --- | --- | --- | --- | --- | --- |
| 국내 주식 (KRX) | 한국투자증권 실시간 호가 WebSocket | WSS | MarketDataWorker | ES `myfin-ohlcv-krx` | [[ref_01_한국투자증권_API]] |
| 국내 가상자산 | 업비트 WebSocket (Ticker) | WSS | MarketDataWorker | ES `myfin-ohlcv-upbit` | — |

## 4. 메모리 프로비저닝 설계 (8GB RAM)

### 4.1 컴포넌트별 RAM 할당표

| 컴포넌트 | 할당 RAM | Docker `mem_limit` | SWAP 허용 | 최적화 설정 |
| --- | --- | --- | --- | --- |
| Elasticsearch 8.x | 2,500 MB | 2,500 MB | **절대 금지** | `-Xms2g -Xmx2g`, G1GC, `bootstrap.memory_lock: true` |
| PostgreSQL 16 | 1,024 MB | 1,024 MB | 허용 | `shared_buffers=256MB`, `work_mem=8MB`, `maintenance_work_mem=64MB` |
| FastAPI (Gunicorn 4 workers) | 768 MB | 768 MB | 부분 허용 | Worker당 ~192MB, `--timeout 30` |
| Celery Workers (최대 4프로세스) | 768 MB | 768 MB | 부분 허용 | `--max-tasks-per-child=100` (메모리 파편화 방지) |
| Redis 7 | 384 MB | 384 MB | 허용 | `maxmemory 384mb`, `maxmemory-policy allkeys-lru` |
| Logstash | 512 MB | 512 MB | 부분 허용 | `-Xms256m -Xmx512m` |
| Nginx | 64 MB | 64 MB | 허용 | `worker_processes auto` |
| **OS 커널 여유분** | **1,024 MB** | — | — | 커널 버퍼·페이지 캐시·가상화 오버헤드 |
| **합계 (애플리케이션)** | **6,020 MB** | | | |
| **총합** | **7,044 MB** | | **최대 4GB SWAP** | |

> [!important] OOM Killer 방지 3원칙
> 1. 각 컨테이너는 `mem_limit`과 `memswap_limit` 모두 설정해야 SWAP 상한도 통제된다.
> 2. Elasticsearch `bootstrap.memory_lock: true` 미적용 시 JVM GC STW(Stop The World) 폭증으로 전체 시스템 응답 불능 가능.
> 3. Celery `--max-tasks-per-child=100` 설정으로 Python GC 이후 메모리 파편화 누적을 주기적으로 초기화한다.

### 4.2 Linux 커널 튜닝 (`/etc/sysctl.d/99-myfin.conf`)

```bash
# SWAP 발생 임계치: 물리 RAM 소진 극대화
vm.swappiness=10

# 더티 페이지 플러시 비율 최적화 (트레이딩 I/O 안정화)
vm.dirty_ratio=15
vm.dirty_background_ratio=5

# 소켓 연결 큐 상한 (WebSocket 다중 연결 대비)
net.core.somaxconn=65535
net.ipv4.tcp_max_syn_backlog=4096

# Elasticsearch 요구 사항 (필수)
vm.max_map_count=262144
```

## 5. 핵심 도메인 설계

### 5.1 API Key 암호화 아키텍처

```text
[등록 흐름]
사용자 입력 (평문 API Key)
    │
    ▼ HTTPS (TLS 1.3) → 전송 중 보호
FastAPI CryptoService.encrypt(raw_key)
    │  ├── 알고리즘: Fernet (AES-128-CBC + HMAC-SHA256, 표준 AES-256 동급 보안)
    │  └── Master Key: OS ENV `MASTER_ENCRYPTION_KEY` (코드·DB 완전 격리)
    ▼
PostgreSQL: encrypted_api_key (Base64 Fernet Token 저장)

[사용 흐름]
PostgreSQL encrypted_api_key
    │
    ▼
CryptoService.decrypt() → 메모리상 평문 (일시적)
    │
    ▼ 증권사 API 호출 (HTTPS)
    │
    ▼ 호출 완료 즉시 메모리 해제 (Python gc.collect())
```

### 5.2 API Key 유형별 생명주기 정책

| 유형 | 예시 증권사 | 만료 특성 | 갱신 주체 | 갱신 트리거 | API 참조 |
| --- | --- | --- | --- | --- | --- |
| `DYNAMIC` | 한국투자증권 | Access Token 24시간 | Celery Beat | 만료 1시간 전 자동 Refresh API 호출 | [[ref_01_한국투자증권_API]] |
| `STATIC` | 바이낸스, 업비트 | 고정 만료일 (6~12개월) | 사용자 수동 | 만료 D-7, D-3, D-0 알림 발송 | — |

### 5.3 Circuit Breaker 패턴 (증권사 API 장애 격리)

각 계좌의 Circuit Breaker 상태는 Redis에 `circuit:{account_id}` 키로 저장된다. 프로세스 재시작 후에도 상태가 유지된다.

| 상태 | 전환 조건 | 동작 |
| --- | --- | --- |
| `CLOSED` (정상) | 초기 상태 | 모든 주문 정상 실행 |
| `OPEN` (차단) | 연속 5회 실패 | 주문 즉시 Reject, NotificationWorker 알림 발송, 60초 후 HALF-OPEN |
| `HALF-OPEN` (시험) | OPEN 후 60초 경과 | 테스트 주문 1회 → 성공 시 CLOSED, 실패 시 OPEN 복귀 |

### 5.4 Kill-Switch 아키텍처

| 범위 | 엔드포인트 | Redis 채널 | 효과 |
| --- | --- | --- | --- |
| 계좌별 | `PATCH /accounts/{id}/kill-switch` | `user:{uid}:events` | 해당 계좌 봇만 즉시 정지 |
| 글로벌 (전체) | `POST /system/kill-switch` | `user:{uid}:global-kill` | 해당 사용자의 모든 계좌 봇 즉시 정지 |

## 6. 인프라 오케스트레이션 (Docker Compose V2)

### 6.1 포트 할당 전략

> [!warning] 기존 실행 중인 서비스 포트 충돌 현황 (2026-06-02 기준)
> 동일 VM에서 아래 포트가 이미 점유되어 있다. myfin 2.0은 충돌 없는 포트로 할당한다.
> - `5432` → `postgres_db` 컨테이너 (finflow 프로젝트)
> - `6379` → `finflow_redis` 컨테이너 (finflow 프로젝트)
> - `8001` → 기존 Python 프로세스
> - `8080` → 기존 Node.js 프로세스

> [!important] 기존 컨테이너 보안 경고
> `postgres_db`(5432)와 `finflow_redis`(6379)가 현재 `0.0.0.0`에 바인딩되어 있다. 이는 내부망이라도 불필요한 노출이다. 기존 프로젝트 `docker-compose.yml`에서 `127.0.0.1:5432:5432` 형식으로 수정 권장.

**myfin 2.0 포트 할당표:**

| 서비스 | 컨테이너 내부 포트 | 호스트 바인딩 | 비고 |
| --- | --- | --- | --- |
| Nginx | 80, 443 | `0.0.0.0:80`, `0.0.0.0:443` | 유일하게 외부 개방 |
| FastAPI | 8000 | **노출 없음** (Docker 내부 통신만) | Nginx가 proxy |
| **PostgreSQL** | 5432 | `127.0.0.1:5433:5432` | **5433** (5432 충돌 회피) |
| **Redis** | 6379 | `127.0.0.1:6380:6379` | **6380** (6379 충돌 회피) |

### 6.4 자체 서명 인증서 (Self-Signed Certificate) 설정

내부망 전용 환경이므로 Let's Encrypt 대신 OpenSSL로 자체 서명 인증서를 발급한다.

**인증서 발급 (VM에서 1회 실행):**

```bash
# 인증서 저장 디렉토리 생성
mkdir -p /etc/nginx/certs

# 자체 CA 키 + 루트 인증서 생성
openssl genrsa -out /etc/nginx/certs/ca.key 4096
openssl req -x509 -new -nodes -key /etc/nginx/certs/ca.key \
  -sha256 -days 3650 -out /etc/nginx/certs/ca.crt \
  -subj "/C=KR/ST=Seoul/O=MyFin Internal CA/CN=MyFin Root CA"

# 서버 키 + CSR 생성
openssl genrsa -out /etc/nginx/certs/myfin.key 2048
openssl req -new -key /etc/nginx/certs/myfin.key \
  -out /etc/nginx/certs/myfin.csr \
  -subj "/C=KR/ST=Seoul/O=MyFin/CN=myfin.local"

# SAN(Subject Alternative Name) 확장 설정
cat > /etc/nginx/certs/myfin.ext << EOF
[v3_req]
subjectAltName = @alt_names
[alt_names]
DNS.1 = myfin.local
IP.1  = 192.168.x.x
EOF

# CA로 서버 인증서 서명 (825일, Apple 정책 준수)
openssl x509 -req -in /etc/nginx/certs/myfin.csr \
  -CA /etc/nginx/certs/ca.crt -CAkey /etc/nginx/certs/ca.key \
  -CAcreateserial -out /etc/nginx/certs/myfin.crt \
  -days 825 -sha256 -extfile /etc/nginx/certs/myfin.ext -extensions v3_req
```

**Nginx TLS 설정:**

```nginx
server {
    listen 443 ssl;
    server_name myfin.local;

    ssl_certificate     /etc/nginx/certs/myfin.crt;
    ssl_certificate_key /etc/nginx/certs/myfin.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;
}

# HTTP → HTTPS 강제 리다이렉트
server {
    listen 80;
    server_name myfin.local;
    return 301 https://$host$request_uri;
}
```

> [!note] 클라이언트 CA 신뢰 등록
> 내부망 내 접속 기기(Mac, Windows)에서 `ca.crt`를 OS 신뢰 루트 인증서로 등록해야 브라우저 경고 없이 접속 가능하다.
> - **Mac:** `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain ca.crt`
> - **Windows:** `certlm.msc` → 신뢰할 수 있는 루트 인증 기관 → 인증서 가져오기
> - **React 개발 서버 (`vite.config.ts`):** `server.https` 옵션에 동일 인증서 적용하여 CORS 쿠키 문제 방지

## 8. 프론트엔드 아키텍처 (React 상태 관리)

### 8.1 상태 분류 원칙

React 상태를 **서버 상태**와 **클라이언트 상태**로 명확히 분리한다. 이 둘을 혼재하면 캐시 무효화 타이밍과 낙관적 업데이트 충돌이 발생한다.

| 상태 유형 | 관리 도구 | 특성 |
| --- | --- | --- |
| **서버 상태** (API 응답 데이터) | **TanStack Query v5** | 자동 캐시·갱신·무효화·재시도. `staleTime` 기반 폴링 |
| **전역 클라이언트 상태** (UI·인증) | **Zustand** | 경량 스토어. Redux 대비 보일러플레이트 90% 감소 |
| **지역 UI 상태** (폼·토글·모달) | React `useState` / `useReducer` | 컴포넌트 범위 내에서만 사용 |
| **URL 상태** (필터·페이지·탭) | **React Router v7** | 공유 가능한 URL로 상태 영속화 |

### 8.2 Zustand 스토어 설계

**스토어는 도메인별로 분리한다. 단일 거대 스토어 금지.**

```typescript
// store/authStore.ts — 인증 상태 (메모리 내 Access Token 포함)
interface AuthState {
  accessToken: string | null      // localStorage 저장 금지. 메모리에만 보관
  userId: number | null
  email: string | null
  setAuth: (token: string, user: { id: number; email: string }) => void
  clearAuth: () => void
}

// store/tradingStore.ts — 실시간 봇·Kill-Switch 상태
interface TradingState {
  globalKillActive: boolean
  accountStatus: Record<number, 'ACTIVE' | 'KILLED'>   // account_id → 상태
  circuitBreaker: Record<number, 'CLOSED' | 'OPEN' | 'HALF_OPEN'>
  setAccountStatus: (accountId: number, status: 'ACTIVE' | 'KILLED') => void
  setCircuitBreaker: (accountId: number, state: 'CLOSED' | 'OPEN' | 'HALF_OPEN') => void
  activateGlobalKill: () => void
}

// store/notificationStore.ts — 인앱 알림 토스트 큐
interface NotificationState {
  queue: Array<{ id: string; type: 'success' | 'error' | 'warning'; message: string }>
  push: (notification: Omit<NotificationState['queue'][0], 'id'>) => void
  dismiss: (id: string) => void
}
```

### 8.3 TanStack Query 도메인별 쿼리 설계

```typescript
// hooks/useAccounts.ts
export const useAccounts = () =>
  useQuery({
    queryKey: ['accounts'],
    queryFn: () => api.get('/accounts'),
    staleTime: 30_000,          // 30초 캐시 (잔고는 별도 실시간 조회)
  })

// hooks/useTradeLogs.ts — 페이지네이션 + 필터
export const useTradeLogs = (params: TradeLogParams) =>
  useQuery({
    queryKey: ['logs', 'trades', params],
    queryFn: () => api.get('/logs/trades', { params }),
    staleTime: 10_000,
    placeholderData: keepPreviousData,  // 페이지 전환 시 깜빡임 방지
  })

// hooks/useKillSwitch.ts — Mutation (쓰기 작업)
export const useKillSwitch = (accountId: number) => {
  const queryClient = useQueryClient()
  const setAccountStatus = useTradingStore(s => s.setAccountStatus)

  return useMutation({
    mutationFn: (isActive: boolean) =>
      api.patch(`/accounts/${accountId}/kill-switch`, { is_active: isActive }),
    onSuccess: (_, isActive) => {
      setAccountStatus(accountId, isActive ? 'ACTIVE' : 'KILLED')  // Zustand 즉시 반영
      queryClient.invalidateQueries({ queryKey: ['accounts'] })      // 서버 상태 갱신
    },
  })
}
```

### 8.4 WebSocket 통합 — 실시간 서버 이벤트 처리

WebSocket 이벤트를 수신하면 Zustand와 TanStack Query 캐시를 동시에 업데이트한다.

```typescript
// hooks/useRealtimeEvents.ts
export const useRealtimeEvents = () => {
  const queryClient = useQueryClient()
  const { setAccountStatus, setCircuitBreaker } = useTradingStore()
  const { push } = useNotificationStore()
  const { accessToken } = useAuthStore()

  useEffect(() => {
    if (!accessToken) return
    const ws = new WebSocket(`wss://myfin.local/ws/events?token=${accessToken}`)

    ws.onmessage = ({ data }) => {
      const event = JSON.parse(data)
      switch (event.event) {
        case 'KILL_SWITCH_CHANGED':
          setAccountStatus(event.data.account_id, event.data.is_active ? 'ACTIVE' : 'KILLED')
          queryClient.invalidateQueries({ queryKey: ['accounts'] })
          break
        case 'ORDER_EXECUTED':
          queryClient.invalidateQueries({ queryKey: ['logs', 'trades'] })
          queryClient.invalidateQueries({ queryKey: ['dashboard'] })
          push({ type: event.data.status === 'SUCCESS' ? 'success' : 'error',
                 message: `${event.data.ticker} ${event.data.order_side} ${event.data.status}` })
          break
        case 'CIRCUIT_BREAKER_STATE':
          setCircuitBreaker(event.data.account_id, event.data.state)
          break
      }
    }

    // 지수 백오프 재연결 (1s → 2s → 4s → max 30s)
    ws.onclose = () => scheduleReconnect(useRealtimeEvents)
    return () => ws.close()
  }, [accessToken])
}
```
