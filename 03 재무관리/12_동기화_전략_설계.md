# 잔고·포지션 동기화 전략 설계서

> **범위:** 계좌 잔고 및 보유 종목(포지션) 동기화 로직, 실시간 동기화 설정, ES 로그 빈도 계산, Logstash 파이프라인 설계

---

## 1. 동기화 모드 설계

### 1.1 `realtime_sync_enabled` 컬럼 (user_accounts 테이블)

```sql
ALTER TABLE user_accounts
  ADD COLUMN realtime_sync_enabled BOOLEAN NOT NULL DEFAULT FALSE;
```

| 값 | 동기화 방식 | 빈도 |
|---|---|---|
| `FALSE` (기본값) | 장 마감 후 1일 1회 Celery Beat 실행 | 16:05 KST (스냅샷 수집) |
| `TRUE` | 장 중 5분 간격 + 매일 16:05 추가 | 장 중 78회/일 + 1회 = **79회/일** |

**설계 근거 — FALSE 기본값:**
- 브로커 API Rate Limit 보호 (KIS: 초당 20건 제한, KIWOOM: `1700` 에러)
- 8GB VM 환경에서 Celery Worker 부하 최소화
- 계좌가 많아질수록 동시 동기화 충돌 위험 → 사용자가 명시적으로 선택

### 1.2 실시간 동기화 대상 API

| 브로커 | 잔고 API | 포지션(보유종목) API |
|---|---|---|
| 한국투자증권 (KIS) | `GET /uapi/domestic-stock/v1/trading/inquire-balance` (TR: `TTTC8434R` / `VTTC8434R`) | 동일 엔드포인트의 `output2` 배열 (`PDNO`, `HLDG_QTY`, `PCHS_AVG_PRIC`, `PRPR`, `EVLU_AMT`, `EVLU_PFLS_AMT`, `EVLU_PFLS_RT`) |
| 키움증권 (KIWOOM) | `POST /api/dostk/acnt` (API-ID: `kt00001`) | 동일 응답의 `acnt_evlt` 배열 |

> **핵심:** 잔고와 포지션은 **단일 API 호출 1회**로 동시에 수신됩니다. 별도 API를 추가로 호출할 필요 없음 → Rate Limit 부담 최소화.

## 2. 동기화 스케줄 및 Celery Beat 설정

### 2.1 전체 태스크 역할 분리

> **설계 원칙:** 용도별로 API와 주기를 분리하여 Rate Limit 보호 + 룰 평가 응답성 확보

| 태스크 | 주기 | API | 목적 |
|---|---|---|---|
| `watch_prices_and_evaluate` | **1분** (장 중) | `ka10001` (종목별 현재가) | 룰 평가 전용 — 가볍고 빠름 |
| `sync_realtime_accounts` | 5분 (장 중, opt-in) | `kt00004` (계좌 전체) | 잔고·수량 정합성, 포지션 UPSERT |
| `collect_balance_snapshots` | 일 1회 16:05 KST | `kt00004` + `kt00001` | 잔고 스냅샷 이력 |

**`watch_prices_and_evaluate`를 `kt00004` 대신 `ka10001`로 쓰는 이유:**
- kt00004: 계좌 전체 조회 (잔고 + 포지션 + 수량) → 무거움, Rate Limit 소비 큼
- ka10001: 종목 1개당 API 1회, 현재가만 조회 → 가볍고 30개 종목도 부담 없음
- 룰 평가에는 "현재가"만 필요 — 수량·잔고는 Redis 캐시 또는 최근 kt00004 결과 재사용

### 2.2 Celery Beat 스케줄

```python
# app/worker/celery_app.py

CELERYBEAT_SCHEDULE = {
    # ── 일일 스냅샷 ────────────────────────────────────────────────────
    "daily-balance-snapshot": {
        "task": "app.worker.tasks.scheduler.collect_balance_snapshots",
        "schedule": crontab(hour=7, minute=5),    # 16:05 KST = 07:05 UTC
    },
    # ── 5분 잔고 동기화 (realtime_sync_enabled=TRUE 계좌) ─────────────
    "realtime-sync-market-hours": {
        "task": "app.worker.tasks.scheduler.sync_realtime_accounts",
        "schedule": crontab(
            minute="*/5",
            hour="0-6",
            day_of_week="1-5",
        ),
    },
    # ── 1분 현재가 감시 + 룰 평가 (신규) ─────────────────────────────
    "price-watch-evaluate": {
        "task": "app.worker.tasks.rule_watcher.watch_prices_and_evaluate",
        "schedule": crontab(
            minute="*/1",
            hour="0-6",           # 09:00~15:31 KST = 00:00~06:31 UTC
            day_of_week="1-5",
        ),
    },
}
```

**장 시간 기준 (KST → UTC):**
```
KST 09:00 → UTC 00:00
KST 15:30 → UTC 06:30
```

## 3. ES 동기화 로그 빈도 계산 및 설계

### 3.1 동기화 이벤트 분류

ES에 모든 동기화 호출을 기록하면 불필요한 볼륨이 발생합니다.  
**이벤트 중요도 기준으로 선별 적재합니다.**

| 이벤트 유형 | ES 적재 여부 | 이유 |
|---|---|---|
| 동기화 성공 (정상) | **❌ 미적재** | Postgres에 스냅샷·포지션 저장으로 충분 |
| 동기화 실패 (API 오류) | **✅ 적재** | 에러 패턴 분석, 알림 연계 |
| 동기화 실패 (토큰 만료) | **✅ 적재** | 토큰 갱신 패턴 분석 |
| 일일 스냅샷 완료 요약 | **✅ 적재** | 수익률 계산 기준선, AI 보고서 입력 |
| 포지션 급변 감지 (+/- 20% 이상) | **✅ 적재** | 이상 거래 감지, 알림 트리거 |

### 3.2 ES 문서량 계산

**가정 조건:**
- 계좌 수: 10개 (realtime: 5개, daily-only: 5개)
- 장중 동기화 빈도: 5분 간격 × 390분(장 시간) = **78회/일**
- 오류율: 일반적으로 1% 미만 (평균 1회/계좌/일)
- 문서 크기: 에러 로그 ~800 bytes, 일일 요약 ~1,200 bytes

```
일별 ES 적재 추정:

[에러 로그]
  realtime 5계좌 × 78회 × 오류율 1% = 약 4건/일
  daily-only 5계좌 × 1회 × 오류율 1% = 0.05건/일 (월 1~2건)
  → 합계: 약 4~5건/일

[일일 스냅샷 요약]
  10계좌 × 1회 = 10건/일

[포지션 급변 감지]
  10계좌 × 1~2건 (이벤트 발생 시만) = 추정 0~20건/일

총 ES 문서: 약 15~35건/일
월간: 약 450~1,050건
연간: 약 5,400~12,600건

문서 평균 크기 1,000 bytes 기준:
  월 스토리지: ~1 MB / 연 스토리지: ~12 MB
```

**결론:** 매우 적은 볼륨. `myfin-sync-logs-*` 인덱스의 ILM은 6개월 보존으로 충분.

## 4. account_positions 테이블 설계

### 4.1 DDL

```sql
CREATE TABLE account_positions (
    id                 BIGSERIAL PRIMARY KEY,
    account_id         INT          NOT NULL REFERENCES user_accounts(id) ON DELETE CASCADE,
    ticker             VARCHAR(30)  NOT NULL,
    name               VARCHAR(100),                    -- 종목명 (표시용)
    quantity           NUMERIC(20, 8) NOT NULL,         -- 보유수량
    avg_cost           NUMERIC(20, 4),                  -- 매수 평균단가
    current_price      NUMERIC(20, 4),                  -- 동기화 시점 현재가
    market_value       NUMERIC(20, 4),                  -- 평가금액 (qty × current_price)
    unrealized_pnl     NUMERIC(20, 4),                  -- 평가손익 (금액)
    unrealized_pnl_pct NUMERIC(8, 4),                   -- 수익률 (%)
    currency           VARCHAR(10)  NOT NULL DEFAULT 'KRW',
    synced_at          TIMESTAMPTZ NOT NULL,
    UNIQUE (account_id, ticker)                         -- UPSERT 기준 (ON CONFLICT)
);

CREATE INDEX idx_positions_account     ON account_positions(account_id, synced_at DESC);
CREATE INDEX idx_positions_ticker      ON account_positions(ticker);
CREATE INDEX idx_positions_account_pnl ON account_positions(account_id, unrealized_pnl_pct DESC);
```

### 4.2 UPSERT 전략

```sql
-- 동기화 시 기존 포지션은 UPDATE, 신규는 INSERT
INSERT INTO account_positions (account_id, ticker, name, quantity, ...)
VALUES (%(account_id)s, %(ticker)s, ...)
ON CONFLICT (account_id, ticker)
DO UPDATE SET
    quantity           = EXCLUDED.quantity,
    avg_cost           = EXCLUDED.avg_cost,
    current_price      = EXCLUDED.current_price,
    market_value       = EXCLUDED.market_value,
    unrealized_pnl     = EXCLUDED.unrealized_pnl,
    unrealized_pnl_pct = EXCLUDED.unrealized_pnl_pct,
    synced_at          = EXCLUDED.synced_at;

-- 청산된 종목 제거 (브로커 응답에 없으면 삭제)
DELETE FROM account_positions
WHERE account_id = %(account_id)s
  AND ticker NOT IN %(active_tickers)s;
```

## 5. Celery 태스크 설계

```python
# app/worker/tasks/scheduler.py

async def collect_balance_snapshots():
    """기존 태스크 — 전체 계좌 일일 스냅샷 (realtime 여부 무관)"""
    # 1. 전체 활성 계좌 조회
    # 2. 각 계좌별 TokenCacheService.get_token()
    # 3. 브로커 어댑터 호출 → 잔고 + 포지션 수신
    # 4. account_balance_snapshots INSERT (UPSERT X → 이력 보존)
    # 5. account_positions UPSERT (ON CONFLICT ticker)
    # 6. ES sync-logs SYNC_DAILY_SUMMARY 적재


async def sync_realtime_accounts():
    """신규 태스크 — realtime_sync_enabled=TRUE 계좌 5분 간격 동기화"""
    # 1. realtime_sync_enabled=TRUE 계좌만 조회
    # 2. 현재 시각 KST 09:00~15:30 범위 확인 (범위 외면 조기 종료)
    # 3. 각 계좌별 잔고 + 포지션 갱신 (스냅샷은 적재하지 않음 — 과도한 이력 방지)
    # 4. account_positions UPSERT만 수행
    # 5. 오류 발생 시 ES sync-logs SYNC_ERROR_* 적재 + 알림
```

### 5.1 스냅샷 vs 실시간 동기화 데이터 차이

| 동작 | account_balance_snapshots | account_positions |
|---|---|---|
| 일일 스냅샷 (`collect_balance_snapshots`) | INSERT (이력 보존) | UPSERT |
| 실시간 동기화 (`sync_realtime_accounts`) | **INSERT 안 함** | UPSERT |

> **이유:** 실시간 동기화마다 스냅샷 INSERT 시 일일 78건 × 10계좌 = 780행/일.  
> 수익률 계산은 하루 1개 스냅샷 기준으로 충분하므로 실시간은 포지션만 갱신.

## 6. Logstash 파이프라인 설계

> 실제 설정 파일 위치: `infra/logstash/pipeline/myfin.conf`

### 6.1 파이프라인 흐름

```
Celery Worker (Python)
    │
    └── HTTP POST → Logstash :5044 (Beats/HTTP Input)
                        │
                        ├── [filter] 민감 데이터 마스킹
                        │     api_key, secret_key, access_token → "****"
                        │     refresh_token → "****"
                        │
                        ├── [filter] 인덱스 라우팅 결정
                        │     event_type = TRADE_LOG   → myfin-trade-logs-{+YYYY.MM}
                        │     event_type = SYNC_*      → myfin-sync-logs-{+YYYY.MM}
                        │     event_type = APP_LOG     → myfin-app-logs-{+YYYY.MM}
                        │
                        └── [output] Elasticsearch :9200
```

### 6.2 `infra/logstash/pipeline/myfin.conf` 명세

```conf
input {
  http {
    host => "0.0.0.0"
    port => 5044
    codec => "json"
  }
}

filter {
  # ── 민감 데이터 마스킹 ────────────────────────────────────────
  mutate {
    replace => {
      "[api_key]"      => "****"
      "[secret_key]"   => "****"
      "[access_token]" => "****"
      "[refresh_token]"=> "****"
    }
  }

  # ── raw_response 내 토큰 패턴 마스킹 (정규식) ──────────────
  if [raw_response] {
    mutate {
      gsub => [
        "raw_response", "\"access_token\"\\s*:\\s*\"[^\"]+\"", "\"access_token\":\"****\"",
        "raw_response", "\"appkey\"\\s*:\\s*\"[^\"]+\"",       "\"appkey\":\"****\"",
        "raw_response", "\"appsecret\"\\s*:\\s*\"[^\"]+\"",    "\"appsecret\":\"****\""
      ]
    }
  }

  # ── 타임스탬프 정규화 ─────────────────────────────────────────
  if [timestamp] {
    date {
      match    => [ "timestamp", "ISO8601" ]
      target   => "@timestamp"
      timezone => "UTC"
    }
    mutate { remove_field => ["timestamp"] }
  }

  # ── 인덱스명 결정 ──────────────────────────────────────────────
  if [event_type] =~ /^TRADE_/ {
    mutate { add_field => { "[@metadata][target_index]" => "myfin-trade-logs" } }
  } else if [event_type] =~ /^SYNC_/ {
    mutate { add_field => { "[@metadata][target_index]" => "myfin-sync-logs" } }
  } else {
    mutate { add_field => { "[@metadata][target_index]" => "myfin-app-logs" } }
  }
}

output {
  elasticsearch {
    hosts            => ["http://elasticsearch:9200"]
    index            => "%{[@metadata][target_index]}-%{+YYYY.MM}"
    action           => "index"
    manage_template  => false
  }
}
```

## 9. 메모리 영향 분석

8GB VM 환경에서 신규 구성 요소 추가 시 영향:

| 서비스 | 현재 | 추가 후 | 비고 |
|---|---|---|---|
| Elasticsearch | 0 (미실행) | 2,500 MB | G1GC, memory_lock |
| Logstash | 0 (미포함) | 640 MB | LS_JAVA_OPTS: -Xmx512m |
| 기존 서비스 합계 | ~2,500 MB | ~2,500 MB | FastAPI·Celery·Redis·PG |
| **총합** | ~2,500 MB | **~5,640 MB** | 여유: ~2,360 MB |

> **판단:** OS 예약 1GB 포함 총 ~6,640 MB 사용. 8GB 한도 내에서 **안전** (여유 1,360 MB).
> 단, Logstash는 초기 Heap 256m → 512m JVM Warm-up 시 일시적 spike 가능.
> `mem_limit: 640M`, `memswap_limit: 640M` Hard Limit 설정 권장.

## 10. 1분 단위 현재가 감시 + 룰 평가 아키텍처

> **목표:** 모바일로 매입한 종목을 포함하여, 장 중 1분 간격으로 현재가를 추적하고
> 사용자가 설정한 룰(TRAILING_STOP·PRICE_RISE_ALERT·PRICE_BUY)을 자동 평가·실행한다.

### 10.1 전체 흐름

```
[Celery Beat]  매 1분 (장 중, 월~금 09:00~15:30 KST)
      │
      ▼
watch_prices_and_evaluate()
      │
      ├─ 1. DB에서 활성 룰이 있는 계좌 목록 조회
      │      SELECT DISTINCT account_id FROM trading_rules
      │      WHERE is_active = TRUE AND deleted_at IS NULL
      │
      ├─ 2. 계좌별 감시 종목 수집
      │      보유 종목:  account_positions WHERE account_id IN (...)
      │      추가 종목:  PRICE_BUY 룰의 target_ticker (미보유 종목)
      │      → unique_tickers: set
      │
      ├─ 3. 현재가 조회 (종목별, Redis 캐시 우선)
      │      Redis key: price:{ticker}  TTL: 90초
      │      cache miss → ka10001 API 호출
      │      → price_map: {ticker: Decimal}
      │
      ├─ 4. 가용잔고 조회 (PRICE_BUY 룰 있는 계좌만)
      │      Redis key: avail:{account_id}  TTL: 5분
      │      cache miss → kt00001 API 호출 (pymn_alow_amt)
      │      → balance_map: {account_id: Decimal}
      │
      ├─ 5. 최고가 갱신 (TRAILING_STOP 룰 전용)
      │      Redis key: hl:{account_id}:{ticker}  TTL: 없음
      │      if current_price > stored_high: 갱신
      │      → high_map: {(account_id, ticker): Decimal}
      │
      ├─ 6. 룰 평가 (RuleEvaluator.evaluate_all)
      │      계좌별, 룰별 EvalContext 구성 → evaluate()
      │      결과: SKIP | EXECUTE | NOTIFY
      │
      ├─ 7. 실행 / 알림
      │      EXECUTE → broker_adapter.place_order()
      │      NOTIFY  → webhook 발송 (Discord/Slack/Telegram)
      │      실행 후 룰 비활성화 (repeat=false인 경우)
      │
      └─ 8. account_positions 현재가 UPSERT
             ka10001 결과로 current_price 갱신
             (수량·평균단가는 변경 없음 — kt00004 동기화에서 처리)
```

### 10.2 Redis 키 설계 (Price Watch 전용)

| Key 패턴 | Value | TTL | 설명 |
|---|---|---|---|
| `price:{ticker}` | 현재가 (문자열, 원) | **90초** | 1분 주기이므로 90초면 충분 |
| `avail:{account_id}` | 가용잔고 (문자열, 원) | **5분** | 빈번 조회 방지 |
| `hl:{account_id}:{ticker}` | 최고가 추적값 | **없음** | 룰 비활성화 시 수동 삭제 |

**캐시 전략:**
```python
async def get_current_price(ticker: str, token: str, base_url: str) -> Decimal:
    redis  = await get_redis()
    cached = await redis.get(f"price:{ticker}")
    if cached:
        return Decimal(cached)
    
    # ka10001 API 호출
    price = await _fetch_ka10001(ticker, token, base_url)
    await redis.set(f"price:{ticker}", str(price), ex=90)
    return price
```

### 10.3 Rate Limit 분석

**가정:**
- 활성 계좌: 5개
- 계좌당 보유 종목: 평균 5개
- PRICE_BUY 추가 종목: 3개 (중복 제거 후)
- 총 unique 종목: **~15개** (최악 25개)

```
ka10001 호출 (1분당):
  unique_tickers × cache_miss_rate(50%) = 15 × 0.5 = ~8회/분
  → 초당 0.13회 ← Kiwoom 한도(초당 ~5회) 대비 매우 안전

kt00001 호출 (5분당):
  PRICE_BUY 계좌 수 = 최대 5회/5분
  → 무시 가능

전체 API 부하 (1일):
  ka10001: 8회 × 장 390분 = ~3,120회/일 (계좌 5개 기준)
  kt00001: 5회 × 78회 = ~390회/일
  → Kiwoom 일 한도 내 안전
```

### 10.4 Trailing Stop 최고가 추적 상세

```
룰 생성 시:
  1. hl:{account_id}:{ticker} 키 생성
  2. 초기값 = max(현재 avg_cost, 현재가)

1분 watch 루프에서:
  current = price_map[ticker]
  high    = Decimal(await redis.get(f"hl:{account_id}:{ticker}") or "0")
  
  if current > high:
      await redis.set(f"hl:{account_id}:{ticker}", str(current))
      high = current    ← 최고가 갱신
  
  drop_threshold = high * (1 - drop_pct / 100)
  if current <= drop_threshold:
      → EXECUTE (매도) 또는 NOTIFY
      → 룰 비활성화
      → Redis hl 키 삭제

예시 (drop_pct=5):
  매입가: 984,000
  Day 1 고점: 1,066,000  ← Redis 갱신
  Day 2 current: 1,013,700 (= 1,066,000 × 0.95) → 발동!
```

### 10.5 PRICE_BUY 미보유 종목 처리

`PRICE_BUY` 룰은 아직 보유하지 않은 종목도 타겟이 될 수 있습니다.

```python
# 감시 종목 수집 시:
buy_rules = [r for r in active_rules if r.conditions["rule_type"] == "PRICE_BUY"]
extra_tickers = {r.conditions["ticker"] for r in buy_rules}

# account_positions에 없는 종목만 추가 조회
held_tickers  = {p.ticker for p in positions}
watch_tickers = held_tickers | extra_tickers  # 합집합
```

### 10.6 룰 실행 결과 ES 적재 이벤트

| 이벤트 | ES 적재 | 설명 |
|---|---|---|
| 룰 평가 (SKIP) | ❌ 미적재 | 매 분 수백 건 발생, 볼륨 낭비 |
| 룰 발동 (EXECUTE/NOTIFY) | ✅ `RULE_TRIGGERED` | 중요 이벤트 |
| 주문 실행 성공 | ✅ `TRADE_LOG` (기존) | orders 테이블 + ES |
| 주문 실행 실패 | ✅ `RULE_EXEC_ERROR` | 알림 + ES |
| 현재가 조회 실패 | ✅ `PRICE_FETCH_ERROR` | 3회 연속 실패 시만 |

## 11. 동기화 주기별 역할 최종 정리

```
┌──────────────────────────────────────────────────────────────────┐
│  타임라인 (장 중, 매 분)                                          │
│                                                                  │
│  00:00  00:01  00:02  00:03  00:04  00:05  ... 06:30 (UTC)      │
│    │      │      │      │      │      │                          │
│    ▼      ▼      ▼      ▼      ▼      ▼                          │
│  [$]    [$]    [$]    [$]    [$]   [$$]   ← $ = watch_prices    │
│                                    ↑                             │
│                                   [$$] = watch + sync_realtime  │
│                                   (5분마다 kt00004도 실행)       │
└──────────────────────────────────────────────────────────────────┘

$ watch_prices_and_evaluate (1분):
  · ka10001로 현재가 조회 (Redis 캐시)
  · 룰 평가 → EXECUTE/NOTIFY
  · account_positions.current_price UPSERT

$$ + sync_realtime (5분, opt-in):
  · kt00004로 전체 잔고·수량 동기화
  · account_positions UPSERT (수량·평균단가 포함)
  · balance_snapshot은 저장 안 함

일 1회 collect_balance_snapshots (16:05 KST):
  · kt00004 + kt00001 전체 조회
  · account_balance_snapshots INSERT (이력 보존)
  · account_positions UPSERT
```
