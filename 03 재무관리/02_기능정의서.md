## 2. 인증 및 세션 관리 (SYS)

### SYS-01: 회원가입

| 항목 | 내용 |
| --- | --- |
| 입력 | 이메일, 비밀번호 |
| 비밀번호 정책 | 최소 8자, 대/소문자·숫자·특수문자 각 1개 이상 포함 |
| 처리 | Argon2id 해싱 후 PostgreSQL 저장 |
| 수용 기준 | 이미 가입된 이메일 409 반환, 정책 미충족 422 반환 |

### SYS-02: 로그인 / 로그아웃

| 항목 | 내용 |
| --- | --- |
| 로그인 입력 | 이메일, 비밀번호 |
| 로그인 응답 | Access Token (응답 바디) + Refresh Token (HttpOnly + Secure + SameSite=Strict 쿠키) |
| 실패 응답 | 이메일 존재 여부 노출 없이 "이메일 또는 비밀번호가 일치하지 않습니다." 통일 메시지 |
| 로그아웃 | 서버에서 Refresh Token `is_revoked = TRUE`, 쿠키 만료 처리 |
| Rate Limit | IP당 로그인 실패 10회/분 초과 시 429 반환 |

### SYS-03: JWT 세션 관리

| 항목 | 내용 |
| --- | --- |
| Access Token 유효기간 | 60분 (ENV 변수로 조정 가능) |
| Refresh Token 유효기간 | 30일 |
| Refresh Token Rotation | 사용 시마다 기존 토큰 무효화 + 신규 토큰 발급 |
| 탈취 감지 | 이미 무효화된 Refresh Token 재사용 시 해당 사용자 전체 세션 즉시 무효화 |
| 다중 디바이스 | `user_sessions` 테이블에 세션별 IP·UA 기록. 세션 독립 무효화 지원 |

## 3. 계좌 및 API Key 관리 (AST)

### AST-01: API Key 등록·수정·삭제

| 항목 | 내용 |
| --- | --- |
| 입력 | alias, broker_name, account_number, api_key, secret_key, token_type, expired_at |
| 암호화 | 수신 즉시 Fernet(AES-128-CBC + HMAC) 암호화. 원문은 로그에도 기록하지 않음 |
| 응답 | API Key 원문은 어떠한 응답에도 포함하지 않음 |
| 삭제 | 소프트 삭제 (`deleted_at`). 주문 이력 보존 |
| 수용 기준 | 동일 broker + account_number 중복 등록 409 반환 |

### AST-02: 다중 계좌 관리

| 항목 | 내용 |
| --- | --- |
| 지원 증권사 (v1) | 한국투자증권(`korea_investment`), 업비트(`upbit`), 바이낸스(`binance`, `binance_futures`) |
| 계좌별 별칭 | 사용자 지정 alias 필드 지원 |
| 소유권 격리 | JWT `user_id`와 계좌 `user_id` 불일치 시 403 반환. 타 사용자 계좌 접근 불가 |

### AST-03: 실시간 잔고 조회

| 항목 | 내용 |
| --- | --- |
| 방식 | 대시보드 진입 시 증권사 API 직접 호출 (실시간) + DB 스냅샷 최근값 표시 |
| 스냅샷 수집 | Celery Beat가 매일 장 마감 후 일괄 수집 → `account_balance_snapshots` 저장 |
| 수익률 계산 | 금일 스냅샷과 전일 스냅샷 비교 |

### AST-04: 종목 마스터 관리

| 항목 | 내용 |
| --- | --- |
| 관리 방식 | 시스템 운영자(관리자)가 사전 등록. 사용자가 직접 추가 불가 (v1) |
| 자동 갱신 | Celery Beat가 증권사 API에서 종목 리스트를 주기적으로 동기화 |
| 필드 | ticker, name, market_type, is_trading |

### AST-05: 관심종목 (Watchlist)

| 항목 | 내용 |
| --- | --- |
| 그룹 생성 | 사용자가 임의 이름으로 그룹 생성 가능 |
| 종목 추가/제거 | 그룹에 stocks 마스터 기반 종목 추가·제거 |
| 중복 방지 | 동일 그룹에 동일 종목 중복 등록 DB UNIQUE 제약으로 방지 |

## 4. 자동 트레이딩 코어 (TRD)

### TRD-01: 매매 룰 CRUD

| 항목 | 내용 |
| --- | --- |
| 룰 구성 요소 | conditions (JSONB) + actions (JSONB) |
| 소유권 | 계좌 소유자만 해당 계좌의 룰 생성·수정·삭제 가능 |
| 소프트 삭제 | `deleted_at` 마킹. 과거 주문의 `rule_id` 참조 보존 |

**v1 지원 지표 (Indicator) 상세:**

| 지표 | indicator 값 | 설명 | 필수 파라미터 |
| --- | --- | --- | --- |
| 이동평균 교차 | `MA_CROSS` | 단기·장기 이평선 골든/데드크로스 | `short_term`, `long_term`, `trigger` |
| RSI | `RSI` | 과매수(70+)/과매도(30-) 신호 | `period`, `threshold`, `trigger` |
| 볼린저밴드 | `BOLLINGER_BAND` | 밴드 상단/하단 이탈 | `period`, `std_dev`, `trigger` |
| 가격 돌파 | `PRICE_BREAKOUT` | 특정 절대 가격 기준 돌파 | `price`, `trigger` |

**v1 지원 액션 (Action) 상세:**

| 항목 | 허용값 | 설명 |
| --- | --- | --- |
| `order_side` | `BUY`, `SELL` | 매수/매도 |
| `order_type` | `MARKET`, `LIMIT` | 시장가/지정가 |
| `amount_type` | `PERCENTAGE`, `FIXED_KRW`, `FIXED_QUANTITY` | 수량 결정 방식 |
| `stop_loss_pct` | 0.1 ~ 50.0 | 손절 비율 (선택) |
| `take_profit_pct` | 0.1 ~ 100.0 | 익절 비율 (선택) |

### TRD-02: 자동 트레이딩 봇 실행 엔진

| 항목 | 내용 |
| --- | --- |
| 실행 주체 | Celery TradingBotWorker (계좌별 독립 프로세스) |
| 조건 평가 | 시세 WebSocket 수신 → Indicator 계산 → conditions 만족 시 주문 실행 |
| 프로세스 격리 | 계좌 A의 봇 장애가 계좌 B 봇에 영향 없음 |
| 메모리 보호 | `--max-tasks-per-child=100` (100 태스크 후 자동 재시작) |
| 주문 실행 흐름 | Rule 조건 충족 → 증권사 API 호출 → `orders` 테이블 INSERT → ES 로그 적재 |

### TRD-03: 계좌별 Kill-Switch

| 항목 | 내용 |
| --- | --- |
| 트리거 | `PATCH /accounts/{id}/kill-switch { "is_active": false }` |
| 반응 속도 | ≤ 2초 (Redis Pub/Sub RTT 포함) |
| 효과 | 해당 계좌 Celery Worker 신규 주문 요청 즉시 중단 |
| 복구 | `is_active: true`로 재활성화 |
| UI 반영 | WebSocket으로 즉시 상태 업데이트 |

### TRD-04: 글로벌 Kill-Switch

| 항목 | 내용 |
| --- | --- |
| 트리거 | `POST /system/kill-switch { "activate": true }` |
| 효과 | 사용자의 **모든** 계좌 봇 즉시 중단 |
| 알림 | Kill-Switch 실행 즉시 Discord/Slack 알림 발송 |
| 복구 방법 | 글로벌 Kill-Switch는 자동 복구 없음. 계좌별 `is_active: true`로 수동 재활성화 |

### TRD-05: Circuit Breaker

| 항목 | 내용 |
| --- | --- |
| 상태 저장소 | Redis `circuit:{account_id}` 키 |
| 차단 조건 | 연속 5회 증권사 API 호출 실패 |
| OPEN 유지 시간 | 60초 |
| 복구 | 60초 후 HALF-OPEN → 1회 테스트 성공 시 CLOSED |
| 알림 | OPEN 상태 전환 시 `CIRCUIT_BREAKER_OPEN` 이벤트 알림 발송 |

### TRD-06: 페이퍼 트레이딩 (모의투자)

| 항목 | 내용 |
| --- | --- |
| 활성화 방법 | 룰 생성/수정 시 `is_paper_mode: true` |
| 동작 | 증권사 API 호출 없이 DB에 가상 주문 기록 (`orders.is_paper = TRUE`) |
| 잔고 | 별도 가상 잔고 풀 미사용. 계좌 실제 잔고를 시뮬레이션 기준으로 참조 |
| 로그 분리 | 체결 로그 조회 시 `is_paper` 필터로 실거래와 구분 |
| 수용 기준 | 페이퍼 주문은 알림 발송 대상에서 제외 |

## 5. 로그 및 분석 (LOG)

### LOG-01: 매매 체결 로그 조회

| 항목 | 내용 |
| --- | --- |
| 데이터 소스 | Elasticsearch `myfin-trade-logs-*` |
| 필터 | account_id, rule_id, ticker, order_side, status, 날짜 범위, is_paper |
| 페이지네이션 | 기본 20건, 최대 100건/페이지 |
| 정렬 | `ordered_at DESC` 고정 |

**로그 status 값 정의:**

| status | 의미 | 원인 |
| --- | --- | --- |
| `PENDING` | 주문 요청 중 | 증권사 응답 대기 |
| `SUCCESS` | 체결 완료 | 정상 체결 |
| `PARTIAL` | 부분 체결 | 잔량 미체결 |
| `CANCELLED` | 취소 | 사용자 또는 시스템 취소 |
| `ERROR_API` | API 에러 | Key 만료, 권한 없음, 증권사 서버 오류 |
| `ERROR_FUNDS` | 잔고 부족 | 주문 가능 금액 초과 |
| `TIMEOUT` | 타임아웃 | 증권사 API 30초 내 미응답 |

### LOG-02: 에러 로그 필터링

| 항목 | 내용 |
| --- | --- |
| 목적 | 봇 이상 동작 모니터링. `ERROR_*`, `TIMEOUT` 상태만 빠르게 확인 |
| 동작 | `/logs/errors` 엔드포인트 = `status IN (ERROR_API, ERROR_FUNDS, TIMEOUT)` 필터 고정 |

## 7. AI 분석 보고서 (AIN)

### AIN-01: AI 보고서 자동 생성 (주기)

| 항목 | 내용 |
| --- | --- |
| 생성 주기 | **매주 일요일 00:00 KST** (주간 보고서) + **매월 1일 00:00 KST** (월간 보고서) |
| 실행 주체 | Celery Beat 스케줄러 → Celery SchedulerWorker |
| 데이터 소스 | Elasticsearch 집계 (해당 기간 체결 로그, 수익률, 에러율, 슬리피지) |
| LLM 연동 | OpenAI GPT-4o API (또는 대체 모델). 집계 결과를 프롬프트로 전달 |
| 프롬프트 구조 | 집계 통계 JSON + "이번 주 봇 성과 분석 및 개선점을 마크다운으로 작성해주세요" |
| 저장 | `ai_reports` 테이블에 마크다운 원문 + `performance_summary` JSONB 저장 |
| 알림 | 생성 완료 시 `AI_REPORT_READY` 이벤트 발송 |

### AIN-02: AI 보고서 수동 생성

| 항목 | 내용 |
| --- | --- |
| 트리거 | `POST /reports/generate` |
| 입력 | `period_type`, `period_start`, `period_end` |
| Rate Limit | 사용자당 1회/시간 (LLM API 비용 통제) |
| 응답 | 202 Accepted + 예상 완료 시간 반환. 완료 시 WebSocket + 알림 발송 |
| 중복 방지 | 생성 중인 보고서 존재 시 409 반환 |

### AIN-03: AI 보고서 이력 관리

| 항목 | 내용 |
| --- | --- |
| 목록 | 생성일 내림차순, period_type 필터 지원 |
| 상세 | `content_markdown` + `performance_summary` 전체 반환 |
| 삭제 | v1에서는 삭제 기능 미제공 (이력 보존 정책) |

## 8. 알림 (NTF)

### NTF-01: 외부 메신저 알림

| 항목 | 내용 |
| --- | --- |
| 지원 채널 | Discord Webhook, Slack Webhook (v1) |
| 발송 주체 | Celery NotificationWorker (비동기 큐) |
| 이력 | `notification_logs` 테이블에 발송 성공/실패 기록 |
| 중복 방지 | 동일 `event_type` + `user_id` + 24시간 내 동일 이벤트 중복 발송 방지 |

**알림 이벤트 및 메시지 템플릿:**

| 이벤트 | 발송 조건 | 메시지 예시 |
| --- | --- | --- |
| `ORDER_SUCCESS` | 체결 완료 | `[MyFin] ✅ 체결 완료\n계좌: 메인 국장 계좌\nBTC 매수 0.001개 @ 85,050,000원` |
| `ORDER_ERROR` | 주문 실패 | `[MyFin] ❌ 주문 실패\n원인: API Key 만료\n계좌: 메인 국장 계좌` |
| `API_KEY_EXPIRY_7D` | 만료 7일 전 | `[MyFin] ⚠️ API Key 만료 예정 (7일 후)\n증권사: 바이낸스` |
| `API_KEY_EXPIRY_3D` | 만료 3일 전 | `[MyFin] ⚠️ API Key 만료 예정 (3일 후)\n증권사: 바이낸스` |
| `API_KEY_EXPIRY_TODAY` | 만료 당일 | `[MyFin] 🚨 API Key 오늘 만료!\n즉시 갱신이 필요합니다.` |
| `CIRCUIT_BREAKER_OPEN` | CB 차단 전환 | `[MyFin] 🔴 Circuit Breaker 차단\n계좌: 바이낸스 계좌 (연속 5회 실패)` |
| `AI_REPORT_READY` | 보고서 생성 완료 | `[MyFin] 📊 주간 AI 보고서가 생성되었습니다.` |
| `KILL_SWITCH_ACTIVATED` | Kill-Switch 실행 | `[MyFin] 🛑 Kill-Switch 실행됨\n모든 자동매매가 중단되었습니다.` |

### NTF-02: API Key 만료 사전 경고

| 항목 | 내용 |
| --- | --- |
| 실행 주체 | Celery Beat (매일 09:00 KST) |
| 로직 | `token_type = 'STATIC'` 계좌 중 `expired_at`이 오늘로부터 ≤ 7일인 계좌 조회 → D-7, D-3, D-0 알림 발송 |
| 중복 방지 | `notification_logs`에서 당일 동일 이벤트 발송 여부 확인 |
