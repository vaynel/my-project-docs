# 브로커 토큰 캐싱 인터페이스 설계서

> **목적:** 증권사별 Access Token 발급·갱신·캐싱 전략을 단일 인터페이스로 추상화하여,
> 브로커 종류와 관계없이 Celery Worker가 일관된 방식으로 토큰을 획득할 수 있도록 정의합니다.

---

## 1. 설계 원칙

| 원칙 | 내용 |
|---|---|
| **단일 진입점** | 토큰은 반드시 `TokenCacheService.get_token(account)` 하나의 메서드로만 획득 |
| **캐시 우선** | Redis 캐시 히트 시 브로커 API 호출 없이 즉시 반환 |
| **원자적 갱신** | 동시 갱신 요청이 들어와도 Redis `SET NX + TTL`로 하나의 Worker만 발급 진행, 나머지는 대기 후 캐시 재조회 |
| **복호화 격리** | API Key·Secret 복호화는 Celery Worker 프로세스 내에서만 수행 (FastAPI 핸들러에서 직접 호출 금지) |
| **만료 전 선제 갱신** | TTL 10분 미만 시 Background 갱신 트리거 (요청 차단 없이) |

---

## 2. Redis 캐시 키 설계

```
Redis Key Format:
  broker_token:{account_id}

TTL:
  KIS   → access_token_token_expired 기준 - 10분 (선제 만료)
  KIWOOM → expires_in 응답값 - 10분

Value (JSON string):
{
  "access_token": "<token_string>",
  "token_type":   "Bearer",
  "expires_at":   "<ISO8601 UTC>",   ← 실제 만료 시각 (UTC)
  "broker_name":  "korea_investment" | "kiwoom",
  "issued_at":    "<ISO8601 UTC>"
}
```

**키 설계 근거:**
- `account_id` 단위로 격리 → A계좌 토큰 갱신이 B계좌에 영향 없음
- prefix `broker_token:` → Redis namespace 분리 (Circuit Breaker prefix `cb:`, Kill-Switch prefix `ks:` 와 충돌 방지)

## 3. 브로커별 토큰 발급 명세

### 3.1 한국투자증권 (KIS)

```
POST {base_url}/oauth2/tokenP
Content-Type: application/json

{
  "grant_type": "client_credentials",
  "appkey":     "<decrypted_api_key>",
  "appsecret":  "<decrypted_secret_key>"
}

응답:
{
  "access_token":                "...",
  "token_type":                  "Bearer",
  "expires_in":                  86400,
  "access_token_token_expired":  "2026-06-03 08:30:00"   ← KST 문자열
}
```

**TTL 계산:**
```python
from datetime import datetime, timezone, timedelta
import pytz

KST = pytz.timezone("Asia/Seoul")
expires_kst = datetime.strptime(resp["access_token_token_expired"], "%Y-%m-%d %H:%M:%S")
expires_kst = KST.localize(expires_kst)
expires_utc = expires_kst.astimezone(timezone.utc)
ttl_seconds = int((expires_utc - datetime.now(timezone.utc)).total_seconds()) - 600  # 10분 선제
```

**재발급 제한:** 6시간 이내 재발급 시 기존 토큰이 그대로 반환됨 → Redis에 저장된 토큰이 유효한 경우 API 호출 자체를 스킵

### 3.2 키움증권 (KIWOOM)

```
POST {base_url}/oauth2/token
Content-Type: application/json
api-id: au10001

{
  "grant_type":  "client_credentials",
  "appkey":      "<decrypted_api_key>",
  "secretkey":   "<decrypted_secret_key>"
}

응답:
{
  "token":       "...",
  "token_type":  "Bearer",
  "expires_in":  86400,
  "scope":       "oob"
}
```

**TTL 계산:**
```python
ttl_seconds = int(resp["expires_in"]) - 600  # 10분 선제 만료
```

> **주의:** 키움 실전/모의 환경은 별도 URL + 별도 appkey/secretkey 세트가 필요합니다.
> 모의 도메인: `https://mockapi.kiwoom.com` (KRX 전용)

## 4. 인터페이스 명세

```python
# app/services/broker_token.py

from abc import ABC, abstractmethod
from dataclasses import dataclass
from datetime import datetime


@dataclass
class TokenInfo:
    access_token: str
    token_type: str        # "Bearer"
    expires_at: datetime   # UTC
    broker_name: str
    issued_at: datetime    # UTC


class BrokerTokenService(ABC):
    """증권사별 토큰 발급·갱신 전략 추상 인터페이스"""

    @abstractmethod
    async def issue_token(self, api_key: str, secret_key: str) -> TokenInfo:
        """브로커 API를 호출하여 신규 토큰 발급"""
        ...

    @abstractmethod
    def needs_refresh(self, token_info: TokenInfo) -> bool:
        """현재 시각 기준 토큰 갱신이 필요한지 판단 (TTL 10분 미만 = True)"""
        ...


class TokenCacheService:
    """Redis 기반 토큰 캐시 통합 서비스 (모든 브로커 공통)"""

    LOCK_TTL = 30          # 갱신 중 분산 락 TTL (초)
    RETRY_WAIT = 0.5       # 락 대기 재시도 간격 (초)
    RETRY_MAX = 10         # 최대 재시도 횟수

    async def get_token(self, account: UserAccount) -> str:
        """
        토큰 획득 진입점. 호출자는 이 메서드만 사용.

        흐름:
        1. Redis에서 캐시 조회
        2. 캐시 히트 + TTL 10분 초과 → access_token 즉시 반환
        3. 캐시 히트 + TTL 10분 미만 → Background 갱신 트리거 후 기존 토큰 반환 (차단 없음)
        4. 캐시 미스 → 분산 락 획득 → 토큰 발급 → Redis 저장 → 반환
        5. 락 획득 실패 (다른 Worker가 갱신 중) → RETRY_WAIT 대기 후 캐시 재조회 반복
        """
        ...

    async def invalidate(self, account_id: int) -> None:
        """토큰 강제 무효화 (API 오류 401/403 수신 시 호출)"""
        ...

    async def _acquire_lock(self, account_id: int) -> bool:
        """Redis SET NX PX {LOCK_TTL*1000} 를 이용한 분산 락"""
        ...

    async def _release_lock(self, account_id: int) -> None:
        ...
```

## 5. 토큰 만료 중 주문 발생 처리 흐름

```
Celery evaluate_and_trade()
    │
    ▼
TokenCacheService.get_token(account)
    │
    ├── [캐시 유효] ──────────────────────────────► 주문 실행
    │
    ├── [TTL < 10분] ─► Background 갱신 spawn ──► 기존 토큰으로 주문 실행
    │                    (non-blocking)
    │
    └── [캐시 없음 / 만료]
             │
             ▼
         분산 락 시도
             │
             ├── [락 획득 성공] ─► 토큰 발급 ─► Redis 저장 ─► 주문 실행
             │
             └── [락 획득 실패 - 다른 Worker 갱신 중]
                      │
                      └── 0.5초 대기 × 최대 10회 재시도 ─► 캐시 재조회
                               │
                               ├── [캐시 복구됨] ─► 주문 실행
                               └── [타임아웃 15초] ─► ORDER ERROR_API 기록 + 알림 발송
```

**결론:** 만료 중 주문은 **최대 15초 대기 후 재시도**, 여전히 실패 시 `ERROR_API` 처리. 무한루프 방지를 위해 재시도 횟수 하드캡.

## 6. 에러 코드 → 토큰 처리 매핑

| HTTP 상태 / 에러코드 | 브로커 | 처리 방식 |
|---|---|---|
| 401 Unauthorized | KIS / KIWOOM | `invalidate()` 후 즉시 재발급 1회 시도 |
| 403 Forbidden | KIS | 동일 |
| `8030 / 8031` | KIWOOM | 실전/모의 환경 불일치 → 알림만 발송, 재시도 없음 |
| `1700` Rate Limit | KIWOOM | 60초 지수 백오프 후 재시도 |
| `1687` Recursive | KIWOOM | 즉시 중단, ERROR_API 기록 |
| 발급 API 자체 5xx | 전체 | 30초 × 3회 재시도, 이후 Circuit Breaker OPEN |

## 7. 메모리 영향

| 항목 | 크기 |
|---|---|
| 토큰 1건 (JSON) | ~500 bytes |
| 계좌 10개 | ~5 KB |
| Redis 메모리 | 무시 가능 (기존 256MB 할당 유지) |
